# MarryMe – Supabase

Database, rules and server functions of MarryMe on Supabase (project
`uidvxjsztnigsqkiprel`). There is no backend of our own: the panel
(`marryme_web`) talks to Supabase directly; the guest app (`marryme`) goes
through the `api` Edge Function, or talks to Supabase directly when the
guest signs in (same accounts as the panel).

## Structure

| Path | What |
| ---- | ---- |
| `supabase/migrations/…_schema.sql` | Tables `weddings`, `invitations`, `guest_messages`, `rsvp_responses`, plan rules and triggers |
| `supabase/migrations/…_access.sql` | Privileges and RLS: each couple only sees its own weddings |
| `supabase/migrations/…_guests.sql` | Guest functions: `open_invitation`, `send_guest_message`, `send_rsvp` |
| `supabase/migrations/…_photos.sql` | `photos` bucket in Storage (public read, uploads only into one's own wedding folder) |
| `supabase/migrations/…_schedule.sql` | pg_cron job calling `notifications` every 5 minutes |
| `supabase/migrations/…_invitation_moments.sql` | Invitations with one or more moments (ceremony, lunch, cake cutting) |
| `supabase/migrations/…_guest_accounts.sql` | Guests with an account: `saved_invitations`, `save_invitations`, `my_invitations`, `forget_invitation`; RSVP responses tied to the user; `wedding_summary` for the couple's page in the app |
| `supabase/functions/api` | Guest app: `GET /invito/<code>`, `POST /messaggi`, `POST /rsvp` (no login) |
| `supabase/functions/payments` | Panel: `POST /checkout`, `POST /verify` (Stripe Checkout, with the couple's token) |
| `supabase/functions/stripe-webhook` | Stripe notifications (signed) |
| `supabase/functions/notifications` | Wedding day and new photos push notifications (Firebase) |
| `supabase/functions/account` | App and panel: `POST /delete` deletes the signed-in user's account, their weddings and photos |

The rules that matter are enforced by the database, so they hold whoever
calls the API: new weddings start on the free plan, the plan only changes
with a payment, full-plan sections and more than 20 invitations answer
`402`, invitation codes are always generated by the database.

## Tests

```sh
./test/run.sh                                        # migrations, on a temporary local Postgres 17
cd supabase/functions && deno test --allow-env tests/  # Edge Functions, with fakes
```

`test/run.sh` needs `brew install postgresql@17`; the functions need
`brew install deno`. No Docker.

## Deploy

```sh
supabase db push --linked          # new migrations
supabase functions deploy --use-api
```

## Settings (once)

**Function secrets** (`supabase secrets set NAME=value`, or Dashboard →
Edge Functions → Secrets):

| Secret | Used by | Without it |
| ------ | ------- | ---------- |
| `PANEL_URL` | payments: return address after paying | `http://localhost:8081` |
| `STRIPE_SECRET_KEY` | payments | checkout answers 503 |
| `STRIPE_WEBHOOK_SECRET` | stripe-webhook | webhook answers 503 (the panel's `verify` still works) |
| `FIREBASE_SERVICE_ACCOUNT` | notifications | notifications are off (503) |

`FIREBASE_SERVICE_ACCOUNT` is the whole JSON of the service account key
(Firebase console → Project settings → Service accounts → Generate new
private key):

```sh
supabase secrets set FIREBASE_SERVICE_ACCOUNT="$(cat firebase-service-account.json)"
```

**Project address for the notifications job** (Dashboard → SQL editor):

```sql
select vault.create_secret('https://uidvxjsztnigsqkiprel.supabase.co', 'project_url');
```

The job's own secret is generated by the migration and stays in the Vault.

**Stripe webhook**: endpoint
`https://uidvxjsztnigsqkiprel.supabase.co/functions/v1/stripe-webhook` with
the `checkout.session.completed` and `checkout.session.async_payment_succeeded`
events; its signing secret goes into `STRIPE_WEBHOOK_SECRET`.

**Guest app**: in Firebase Remote Config, `apiUrl` =
`https://uidvxjsztnigsqkiprel.supabase.co/functions/v1/api`.
